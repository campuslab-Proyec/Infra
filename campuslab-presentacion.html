Sistema de gestión de reservas de laboratorio

Arquitectura de microservicios con Spring Boot, MySQL, RabbitMQ y autenticación Azure AD, contenerizada con Docker Compose y desplegable en AWS EC2.

7 microservicios Spring Boot 3.3 · Java 21 MySQL 8 RabbitMQ Angular + MSAL Docker Compose

02 — Los 7 microservicios

Qué hace cada uno

bookings
● CÓDIGO COMPLETO

Crea y gestiona reservas. Publica cambios de estado a RabbitMQ y registra cada acción en audit vía REST.

:8081 → /api/bookings
audit
● CÓDIGO COMPLETO

Recibe y persiste eventos de auditoría de otros servicios. Expone historial por reserva o por usuario.

:8085 → /api/audit
report
● CÓDIGO COMPLETO

Solo lectura. Calcula KPIs y top de recursos con cache de 30s para simular tiempo real, sin tocar Kafka.

:8084 → /api/report
catalog
○ SCAFFOLD INICIAL

Gestiona stock de laboratorios y recursos (equipos). Base para las reservas de bookings.

:8082 → /api/resources
notify
○ SCAFFOLD INICIAL

Consume la cola de RabbitMQ que publica bookings y envía la notificación al estudiante/operador.

:8083 → consumer
bff
○ PENDIENTE — CRÍTICO

Punto de entrada único: valida el JWT de Azure AD y reenvía la llamada al microservicio de dominio correcto.

:8080 → /api/bff/*

04 — Infraestructura

Todo corre sobre una red Docker compartida

Tres compose.yaml separados en /infra — db, mq y apps — conectados por la red externa campuslab-net. bookings registra cada cambio de estado en audit mediante una llamada REST síncrona, sin pasar por un bus de eventos.

05 — Seguridad

Login único con Azure AD, propagado por MSAL

01

Login en el frontend

Angular usa @azure/msal-angular con redirect flow. El usuario inicia sesión con su cuenta institucional.

02

Token adjunto automáticamente

El MsalInterceptor agrega el JWT a cada llamada HTTP dirigida al BFF, sin código manual por componente.

03

Validación en cada microservicio

Spring Security OAuth2 Resource Server valida el issuer-uri de Azure AD en bookings, audit y report.

04

Rutas protegidas

MsalGuard bloquea el acceso a /catalog, /bookings, /report y /audit sin sesión activa.

06 — Frontend Angular

Cuatro páginas conectadas al BFF

catalog
● En curso

Lista laboratorios y recursos disponibles para reservar.

bookings
● Construida

Crear reserva, filtrar por estado y cambiar el estado de una existente.

report
● Construida

KPIs y top de recursos, con selector de rango (24h / 7d / 30d).

audit
● Construida

Búsqueda de historial de eventos por reserva o por usuario.

Todas consumen environment.bffUrl mediante servicios Angular dedicados (*.service.ts), siguiendo el mismo patrón que catalog.service.ts.

07 — Despliegue en AWS

De Docker Compose local a una instancia EC2

01

Lanzar EC2

Ubuntu 22.04, t3.medium o superior, con par de llaves SSH.

02

Security Group

Abrir 22, 80 y 8080 públicos; 3306 y 5672 solo internos.

03

Instalar Docker

docker.io + docker-compose-plugin vía SSH.

04

Clonar y levantar

git clone de los 8 repos + docker compose up --build -d.

Pendiente de decidir: un solo EC2 (más simple) vs. la topología multi-instancia del enunciado (ec2-apps + ec2-mq + API Gateway con JWT Authorizer).

08 — Estado y pendientes

Qué falta para el alcance completo

CRÍTICO

Código real de ms-campuslab-bff: hoy cada microservicio valida su propio JWT; falta el punto de entrada único que exige el documento.

ALTO

catalog y notify solo tienen scaffold — falta implementar sus endpoints y el consumer de RabbitMQ.

MEDIO

Topología RabbitMQ incompleta: falta el exchange cmd.topic y las colas/DLQ de catalog y audit.

DECISIÓN

Confirmar con la pauta si un solo EC2 con Docker Compose es suficiente, o si se exige la topología multi-instancia con API Gateway real de AWS.
